# Codex 状态页持续在线设计

日期：2026-07-31

## 目标

让 `https://molanjie.github.io/AI-Status-light/` 始终作为固定入口可访问，并让本机 Codex 状态采集链路在 Windows 登录后自动启动、自检和恢复。

本设计采用用户确认的 A 方案。“持续在线”的可验证定义是：

- GitHub Pages 页面不依赖本机进程即可加载。
- 本机关机、未登录、断网或采集进程故障时，页面显示最后一次有效状态、最后同步时间和“采集端离线”。
- Windows 用户登录后，状态服务和公网隧道自动恢复；正常网络条件下 90 秒内重新显示实时状态。
- Node 服务或 Cloudflare 隧道异常退出后，无需手工运行命令或重新发布网页即可恢复。
- 临时隧道地址变化后，网页自动发现新地址。

本设计不承诺本机关机时仍产生新的 Codex 状态，也不承诺 GitHub 或 Cloudflare 自身永不发生平台级故障。

## 现状与问题

- GitHub Pages 已从 `master/docs` 发布，固定页面正常存在。
- `docs/index.html` 写死一个 `trycloudflare.com` 临时地址。
- 本机当前没有监听 `3456` 的状态服务，也没有运行 `cloudflared`。
- 本机没有 Cloudflare 登录信息、命名隧道、相关 Windows 服务或计划任务。
- 现有 `start-mini-watch-public.ps1` 面向另一个 `3001` 端口的 Mini Watch 服务，不会恢复 Codex 状态接口。
- 页面仅在内存中保存最后一次有效状态，刷新页面后会丢失。

## 方案比较

### 采用：临时隧道自恢复 + 稳定地址注册表

继续使用无需 Cloudflare 账号的 Quick Tunnel。本机看门程序负责启动服务、恢复隧道并把最新公网地址发布到独立 GitHub 分支。网页从固定的注册表 URL 获取当前接口地址。

优点是无需新账号、无需付费服务器，并且适配现有 GitHub Pages。代价是本机离线时只能显示最后状态，隧道恢复时间受本机和 Cloudflare 网络影响。

### 未采用：Cloudflare 命名隧道

固定域名更简单，但需要 Cloudflare 账号、受管域名和登录凭据。当前环境不具备这些条件。

### 未采用：云端中继服务

可以让 API 本身持续在线，但需要新增云服务、鉴权、状态上传和密钥管理。对于已确认的 A 方案超出必要范围。

## 架构

系统分为四个独立单元。

### 1. 静态状态页

`docs/index.html` 继续由 GitHub Pages 托管。页面加载不依赖本机。

页面启动时按以下顺序选择状态接口：

1. URL 查询参数中的显式 `api` 地址，便于诊断。
2. `live-status` 分支的地址注册表。
3. 浏览器保存的最近可用接口地址。
4. `file:` 本地打开时的 `http://127.0.0.1:3456`。

发布版不再写死任何 `trycloudflare.com` 地址。页面每 30 秒重新读取地址注册表，并继续每秒轮询当前状态接口。

### 2. 本地状态服务

现有 `server.js` 继续监听 `0.0.0.0:3456` 并提供 `/api/status`。新增轻量 `/api/health`，只返回服务健康、进程启动时间和当前时间，不触发完整状态扫描。

状态接口保持现有数据结构和隐私边界：可返回会话标题、状态和更新时间，不返回对话正文、内部路径或线程 ID。

### 3. Windows 看门程序

新增 PowerShell 看门程序，单实例常驻运行并只管理自己启动的进程。

看门程序职责：

- 每 10 秒检查本地 `/api/health`。
- 本地服务不可用时启动或重启项目的 `server.js`。
- 本地服务健康后启动 Cloudflare Quick Tunnel。
- 从隧道输出中解析公网地址，并验证公网 `/api/status`。
- 公网检查连续失败三次时，只重启看门程序拥有的隧道进程。
- 新地址验证成功后发布地址注册表。
- GitHub 或 Cloudflare 暂时不可用时按递增间隔重试，最长等待 60 秒。
- 日志和 PID 文件写入用户本地应用数据目录，不写入仓库。

进程身份通过 PID 文件和命令行校验共同确认，禁止按进程名批量终止其他 Node 或 Cloudflare 进程。

### 4. 地址注册表

仓库新增独立的 `live-status` 分支，只存放 `endpoint.json`。示例结构：

```json
{
  "schemaVersion": 1,
  "apiBase": "https://example.trycloudflare.com",
  "publishedAt": "2026-07-31T12:00:00.000Z"
}
```

看门程序通过 GitHub API 更新该文件，仅在公网地址发生变化时创建提交。它不修改本地工作区，也不向 `master` 写运行时提交。

网页通过固定 Raw GitHub URL 加载注册表，并附加时间参数避免使用旧缓存。注册表必须经过结构校验，只接受 HTTPS URL 和允许的主机名。

## 自动启动

新增幂等安装脚本，创建名为 `CodexStatusLightWatchdog` 的当前用户计划任务：

- Windows 用户登录时启动。
- 异常退出后每分钟重启。
- 同一任务重复安装时更新配置，不创建副本。
- 运行前验证 Node、GitHub CLI、Cloudflare 可执行文件和 GitHub 登录状态。

这里的“开机恢复”明确指当前用户登录 Windows 后恢复。用户未登录时，GitHub Pages 仍可访问，但采集端显示离线。

## 页面离线语义

页面把最后一次有效响应和保存时间写入 `localStorage`。

- 单次请求失败：保留当前画面，不立即闪烁。
- 连续三轮失败：显示黄色“采集端离线”，保留最后状态和最后同步时间。
- 没有历史状态：显示“正在连接采集端”，随后转为“采集端离线”。
- 地址注册表返回新地址：立即尝试新地址；成功后清除离线提示。
- 状态接口返回明确运行错误：继续使用红色“运行异常”，不与网络离线混淆。

离线期间不得把会话数量清零、伪造空闲状态或把旧状态标成实时状态。

## 安全与隐私

- GitHub Pages、地址注册表和 Quick Tunnel 都是公开入口。
- 不把 GitHub 令牌、Cloudflare 凭据、用户目录或内部文件路径写入仓库和日志。
- 看门程序调用当前用户已有的 GitHub CLI 凭据，令牌不落盘到项目目录。
- 服务响应继续限制为页面必要字段。
- 注册表只接受 `https://*.trycloudflare.com`，诊断查询参数仍允许用户显式覆盖。

## 故障处理

- Node 异常：看门程序重启 Node，原隧道恢复后继续使用。
- 隧道异常：看门程序创建新隧道，验证后更新注册表。
- GitHub 更新失败：保持已验证隧道运行并重试发布，不删除旧注册表。
- Cloudflare 不可用：页面显示采集端离线，看门程序持续退避重试。
- 本机断网或关机：页面从浏览器缓存展示最后状态并标明时间。
- GitHub Pages 或 Raw GitHub 平台故障：属于外部平台故障，不伪报为 Codex 运行异常。

## 验证

### 自动化验证

- 现有 `npm test` 全部通过。
- 新增测试覆盖地址注册表校验、状态源优先级、持久化快照和连续失败阈值。
- PowerShell 脚本提供非破坏性的配置检查模式，验证依赖路径、任务定义和单实例锁。
- `server.js` 的 `/api/health` 返回 `200`，且不调用完整状态读取。

### 运行验证

- 安装计划任务后重新登录，90 秒内本地和公网接口都返回 `200`。
- 终止看门程序拥有的 Node 进程，90 秒内自动恢复。
- 终止看门程序拥有的隧道进程，90 秒内获得新地址并更新注册表。
- 页面在地址变化后 30 秒内自动切换，不重新部署 GitHub Pages。
- 本机关机或断网时，页面仍能加载并显示最后状态和“采集端离线”。
- 网络恢复后页面自动回到实时状态。
- 320px、390px 和桌面视口不产生新的横向溢出。
- GitHub Pages 最新构建成功，固定 URL 返回 `200`。

## 发布顺序

1. 增加健康接口、前端注册表发现和离线持久化。
2. 增加看门程序、安装脚本和测试。
3. 创建并初始化 `live-status` 分支。
4. 发布 `master/docs`。
5. 安装计划任务并启动看门程序。
6. 验证本地接口、公网接口、注册地址和页面自动恢复。
7. 删除发布版中写死的旧临时地址。

## 验收标准

- 固定页面无需本机即可打开。
- 本机离线时页面明确显示采集端离线和最后同步时间。
- Windows 登录后 90 秒内自动恢复实时状态。
- Node 或隧道被终止后 90 秒内自动恢复。
- 隧道地址变化不需要人工修改网页或重新发布。
- 运行时地址更新不修改本地工作树或 `master` 分支。
- 不新增云账号、付费服务或公开密钥。
